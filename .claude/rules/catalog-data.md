# Catalog, merge and local state

Detail moved verbatim from `CLAUDE.md` on 2026-11-25; the always-loaded core is `AGENTS.md`.

### Key data-flow contracts (do not break without a product decision + updated tests)

**The rules themselves are not here.** The bank is the shared `STREAM-BANK` contract, owned by FastMediaSorter Android; its twelve rules, its amendments and its lettered items live in the contract store, and [docs/contracts/STREAM-BANK.md](../../docs/contracts/STREAM-BANK.md) says which of this repo's classes holds each one. What follows is the product side only: the constants, the classes, and the local consequences a rule has here. Where the two disagree, the contract wins and the code is a ticket - never the other way round.

- **Catalog source** is a ZIP at `StreamCatalogService.CatalogUrl` (a FastMediaSorter release asset), read under `STREAM-BANK` rules 1, 2 and 8. Optional `favicon-atlas.png`, capped by `StreamBankReader.MaximumAtlasBytes` - **read the constant and its comment, never a size from prose**; the atlas grows with the channel count. An atlas over that cap is silently dropped, not an error. The whole archive has a separate, larger cap (`StreamCatalogService.MaximumArchiveBytes`), and exceeding *that* one **is** an error - ours, not the contract's.
- **The atlas and the CSV are one pair** (rule 6): `favicon_index` resolves only against the atlas from the *same* ZIP. A bank that arrives without a usable atlas therefore has its indices nulled before the merge (`CatalogRefreshOutcome`, `CatalogSnapshotOutcome`), because the alternative is wrong icons rather than missing ones.
- **A second, optional network artifact**: the channel-preview artwork (`ChannelPreviewArtworkService`), from the same release, under rules 9 and 12. It downloads only after the user accepts the offer, which is what keeps the explicit-refresh rule intact. Three files, in this order and never any other: `artwork-manifest.json`, then `channel-preview-coords.json`, then `channel-preview-tiles.zip` (`ChannelPreviewTilePack`). **Never pin a revisioned artwork name** (SP-0091, `STREAM-BANK` items F/G/G2), and **the manifest's per-file hashes are a diagnostic, not a gate** (item L, SP-0160): a size or hash mismatch is logged and the import proceeds; what gates it is the structural check (the pack opens, entries are decimal slots, a per-tile ceiling of 240x135x4x4 bytes), and an absent or unparseable manifest is "nothing new", never a failure. The set's `stamp` is recorded in `CatalogState.ChannelPreviewArtworkStamp` as a record of what landed, never as a gate - SP-0088 asks every time.
- **Merge protects user data** (rule 5): `CatalogMerger.Merge` keys channels by URL and only ever touches rows whose `SourceOrigin == Catalog`; `MANUAL` and `IMPORTED` (`SourceOrigin.Manual`/`Imported`) rows are never touched by a refresh. Removal is **not** unconditional - it is gated on `CatalogMergeOptions.RemoveMissing`, which the snapshot path deliberately passes as `false`; the same options record also carries `FaviconSource`. Read `CatalogMergeOptions` before assuming a merge mode.
- **Absence from the bank is not authority to delete** (SP-0089, `STREAM-BANK` item D): a catalog row the bank stops listing is deleted only when it carries nothing the user made. Otherwise it is *retired* - `StreamChannel.RetiredAt` is stamped, the row keeps its id so collection membership and listening history stay attached, and a later live-bank refresh listing the URL again clears the field - the bundled snapshot never does, being older than the download that retired the row (`CatalogMergeOptions.RevivesRetired`, SP-0126). Retired means kept, not offered: the row stays in the pinned strip and in its collections and leaves the general list and the random-station draw. What counts as user-made is enumerated **once**, in `UserAuthoredChannels` - every new per-channel user value has to be added there or a refresh will silently delete it.
- **Refresh is explicit only**: there are no automatic background catalog downloads. Do not add any.
- **`RefreshAsync` throws when the download fails** - there is no network fallback inside it. The one thing it retries is the publish window (`STREAM-BANK` rule 11, SP-0107): a 404, a short read or a truncated ZIP is repeated on a short bounded schedule (`PublishWindowRetry.Default`) inside the same user-started, cancellable operation; everything else fails on the first attempt. A first launch without network is *not* empty, though: `SP-0052` **shipped** a bundled catalog snapshot (`BundledCatalogSnapshot`, `CatalogSnapshotService`, `FirstRunCatalogWindow`), applied only on explicit user consent. `StreamsPlayer.Core.csproj` embeds `Resources\catalog-snapshot.zip` and its `RequireBundledCatalogSnapshot` target **fails the build** when it is absent (override: `-p:AllowMissingCatalogSnapshot=true`), and `scripts/release.ps1` makes regenerating it a release blocker. The ticket is `Implemented`, not yet `Verified` - describe it as shipped and awaiting manual verification.
- **Local state** lives at `%LOCALAPPDATA%\StreamsPlayer` - `catalog-state.json` (written atomically via temp file + move), `favicon-atlas-<guid>.png` (unreferenced ones are pruned on every save), the `grid-previews/` cache, and the last ten launches' logs (`Current.log` plus `Session-<yyyyMMdd-HHmm>.log`, retired and pruned on launch by `DiagnosticLogFiles`; the session stamp is local time). Persisted via `CatalogState` (a record; JSON with per-enum *tolerant* converters wired in `StreamCatalogStore`, so one unreadable enum value costs that field and not the whole state). **`CatalogState` is not the only document there**, and the others are deliberate rather than stray: `quality-memory.json` (SP-0071), `browsing-session.json` (SP-0067), `player-geometry.json` (SP-0084), the settings window's navigation context `settings-ui.json` (SP-0191: last page, group expansion, per-page viewport anchors, window rectangle), the interface profile `ui-profile.json` (SP-0231: input profile and interface size, read once at start-up by `UiProfileService`), the TV schedule's `tv-schedule.json` + `tv-schedule-bindings.json` (SP-0075: a user-supplied XMLTV address, fetched only on the Download schedule button in Settings, bounded by `TvScheduleLimits`) and the remote-control target's `remote-control.json` + `remote-command-ring.json` + `remote-command-log.json` (STRWIN-0303: the listening switch and grants, the replay ring, the last 500 log lines; `RemoteControlStore`) each sit in their own small file, keyed by normalized URL or standing alone. Two reasons decide that split every time, so weigh both before adding a field to `CatalogState`: a save rewrites the whole ~15 MB document, and a per-channel value stored *inside* it must be enumerated in `UserAuthoredChannels` or a refresh silently deletes it (SP-0089). A sibling file is out of both paths, and losing one costs only what it remembered.
